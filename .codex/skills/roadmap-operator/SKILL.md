# Roadmap Operator

## 개요

이 프로젝트 범위 skill은 실행계획의 상태를 찾고 전이할 때 읽는 문맥을 최소화한다. 실행계획 파일의
상단 메타데이터가 유일한 정본이고, 생성된 로드맵은 그 메타데이터에서 나온 색인이다.
로드맵의 상태·제목·다음 행동을 직접 고치지 말고 원본 헤더를 고친 뒤 renderer를 실행한다.

## 실행계획 작성 계약

이 저장소의 실행계획은 구현 코드의 대체물이 아니라, 작업자가 추가 설계 없이 순서대로 실행하고 각
결과를 검증할 수 있는 작업 목록이다. 범용 planning skill이 코드 예시를 요구하더라도 이 저장소에서는
아래 형식이 우선한다.

계획을 쓰기 전에 현재 파일을 확인하고 각 태스크를 하나의 독립적으로 검토·검증 가능한 결과로 나눈다.
각 태스크에는 다음 항목을 모두 적는다.

- 결과: 태스크가 끝났을 때 관찰 가능한 단일 완료 상태
- 대상: 생성·수정·검증할 정확한 경로와 현재 기준 `L시작-L끝`; 새 파일은 `새 파일`로 표시
- 예상 변경량: 파일별 추가·수정·삭제 라인 수의 추정치와 태스크 합계
- 실행 절차: 테스트 실패 확인, 최소 변경, 관련 검증, diff 확인의 순서와 정확한 실행 명령
- 완료 증거: 기대하는 테스트 결과, 산출물, 또는 관찰 가능한 상태
- 의존성: 선행 태스크의 결과를 사용할 때 그 태스크와 인터페이스·산출물 이름

계획에는 구현 코드, 테스트 코드, diff, 의사코드 예시를 넣지 않는다. 대신 변경할 동작, 계약, 심볼,
테스트 사례, 실행 명령과 기대 결과를 자연어로 명시한다. 라인 범위와 예상 변경량은 계획 작성 시점의
근거 있는 작업 경계이며, 실행 중 파일이 달라지면 구현 전에 다시 확인한다.

하나의 계획이 여러 독립 서브시스템·배포 단계·별도 승인 경계를 함께 포함하거나, 태스크를 위 형식의
단일 검증 결과와 구체적인 라인 범위로 한정할 수 없으면 계획을 억지로 작성하지 않는다. 먼저 로드맵
단계를 각각 독립적으로 완료·검증 가능한 순서로 나누는 안을 사용자에게 제안하고, 승인된 단계별로
별도 실행계획을 작성한다.

## 네 가지 읽기 범위 (순서 고정)

1. `docs/CURRENT_STATE.md L1-L28`과 생성된 `docs/ROADMAP.md`를 시작부터 마지막 비완료 행까지 읽는다.
2. 선택한 실행계획 파일의 시작부터 첫 `##` 직전까지만 읽는다.
3. 그 헤더의 `참고 범위`에 적힌 각 파일의 명시된 `L시작-L끝`만 읽는다.
4. 범위 밖 문맥이 반드시 필요하면 읽기 전에 확장을 선언한다. 선언에는 경로, 시작줄, 끝줄, 이유를
   모두 쓰고, 사용자에게 알리거나 작업 기록에 남긴 뒤에만 읽는다.

다른 실행계획의 본문, 완료 계획, `ARCHITECTURE.md` 전체는 위 네 범위만으로 부족하다는 근거가 있을
때만 확장한다. 따라서 이 자료들은 기본적으로 읽지 않는다. 계획 본문을 미리 훑거나 전체 문서를
출력·복사해 컨텍스트를 채우지 않는다.

## 빠른 참조

| 목적 | 기준 또는 명령 |
| --- | --- |
| 시작·재개 | roadmap의 `Picked Up` 또는 첫 `Todo` 행과 선택한 헤더 |
| 새 계획 작성 | 무코드 태스크, 현재 라인 범위, 예상 변경량, 실행 명령, 완료 증거 |
| 헤더 변경 후 생성 | `python scripts/render_roadmap.py` |
| 작업 트리 검증 | `python scripts/check_roadmap.py` |
| staged 검증 | `python scripts/check_roadmap.py --staged` |
| 범위 확장 | path, 시작줄, 끝줄, 이유를 먼저 기록 |

## 상태 전이

- `todo/`에는 `Todo`만 둔다. 착수하면 헤더를 `Picked Up`으로 바꾸고 같은 파일명으로 `active/`로
  이동한다. 저장소 전체의 `Picked Up`은 하나 이하여야 한다.
- `active/`에서는 `Todo`, `Picked Up`, `Blocked`를 사용한다. 막힌 경우 차단 사유와 재개 조건을
  계획 기록에 남긴다.
- 검증을 마친 계획은 헤더를 `Done`으로 바꾸고 같은 파일명으로 `completed/`로 이동한다. 결과와
  잔여 작업을 본문에 기록한다.
- 사용자가 실행하지 않기로 결정한 계획은 `폐기 사유`와 `다음 행동: 없음.`을 기록하고 `Dropped`로
  바꾼 뒤 `dropped/`로 이동한다. 기존 구현과 commit은 삭제하지 않으며 재개 시 새 계획을 만든다.
- 각 전이는 먼저 헤더와 선언된 범위를 읽고, 메타데이터·파일 위치를 함께 바꾼 다음 renderer와
  checker를 실행한다. `docs/ROADMAP.md`를 손으로 수정하지 않는다.

상태 전이 전후에는 짧은 읽은 범위 보고를 남긴다. 최소 형식은 다음과 같다.

```text
전이 전 읽은 범위: path=docs/exec-plans/todo/0000-example.md, 시작줄=1, 끝줄=10, 이유=현재 상태 확인
전이 후 읽은 범위: path=docs/exec-plans/active/0000-example.md, 시작줄=1, 끝줄=10, 이유=Picked Up 검증
```

파일을 이동하지 않은 전이는 같은 path를 반복하고, 범위 밖 자료를 읽었다면 그 항목도 같은 형식으로
추가한다. 보고는 읽은 파일·범위·이유만 담아 간결하게 유지한다.

## Orchestration 실행

`OC-*`가 `Picked Up`이면 일반 Todo를 임의로 선택하지 않고 OC 자식 표를 따른다.

1. 가장 높은 우선순위에서 선행 작업이 모두 `Done`인 `준비 중` 자식을 고른다.
2. 소유 범위가 서로 겹치지 않는 작업만 같은 파동에 넣고, 통합 담당자를 제외한 가용 슬롯 안에서
   독립 worktree·branch로 병렬 실행한다.
3. 배정 시 `실행 중`, focused 검증과 리뷰 통과 시 `통합 대기`, 기준 branch 반영 시 `검증 중`으로
   전이한다.
4. 통합 검증 후 부모 `오케스트레이션` 연결만 남기고 실행용 OC 필드를 제거한 뒤 `Done`으로
   `completed/`에 이동한다.
5. 모든 자식이 Done이고 OC 전체 검증이 통과한 뒤에만 부모를 완료한다.

공유 roadmap·계획 메타데이터와 여러 자식이 함께 건드리는 파일은 통합 담당자만 수정한다. 준비된
자식이 있으면 다른 자식의 차단만으로 OC 전체를 막지 않는다.

## 검증 명령

메타데이터를 변경한 뒤 다음 명령을 순서대로 실행한다.

```powershell
.\scripts\run_python.ps1 scripts/render_roadmap.py
.\scripts\run_python.ps1 scripts/check_roadmap.py
```

staged 상태를 확인할 때는 `python scripts/check_roadmap.py --staged`를 사용한다. renderer만
`docs/ROADMAP.md`를 쓰며 checker는 읽기 전용이다. 실패하면 원본 헤더를 고치고 renderer를 다시
실행한다.

## 흔한 오류

- roadmap 행이나 상태를 직접 편집하는 것 — 헤더를 바꾸고 `python scripts/render_roadmap.py`를 실행한다.
- 계획 본문·완료 계획·전체 아키텍처를 먼저 읽는 것 — 선택한 헤더와 `참고 범위`부터 확인한다.
- 범위 확장 선언 없이 파일을 여는 것 — path, 시작줄, 끝줄, 이유를 먼저 기록한다.
- 전이 전후에 읽은 범위를 보고하지 않는 것 — 위의 두 줄 형식을 사용한다.
- 실행계획에 구현·테스트 코드나 diff를 넣는 것 — 동작·계약·심볼·테스트 사례와 명령으로 바꾼다.
- 라인 범위나 예상 변경량 없이 파일명만 적는 것 — 현재 파일을 확인하고 태스크별 작업 경계를 수치화한다.
- 서로 독립적으로 완료할 수 있는 큰 범위를 한 계획에 넣는 것 — 로드맵 단계 분할안을 먼저 제안한다.
- Windows Codex sandbox에서 기존 `.uv-cache` 또는 `.venv`의 lock 접근 오류가 난 뒤
  `uv run`을 반복하는 것 — 저장소의 `scripts/run_python.ps1`을 사용한다.
