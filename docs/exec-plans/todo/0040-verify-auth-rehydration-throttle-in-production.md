# 0040: 탭 재포커스 시 /v1/auth/me 재호출 - 배포 후 실제로 잡혔는지 검증

상태: `제안됨 · 미착수`

제안 출처: 2026-08-08 사용자가 배포된 `law-rag-web.vercel.app`에서 탭을 왔다갔다 할 때
`/v1/auth/me`가 여전히 계속 호출된다고 보고했다. [0034](../active/0034-web-auth-rehydration-throttle.md)
(같은 날 구현·커밋됨)가 정확히 이 문제를 다루는데, 확인해보니 **0034는 로컬 커밋만 있고
아직 `git push`·배포가 안 된 상태**였다 - 사용자도 재현 환경이 배포된 사이트였음을
확인했다. 그래도 "이건 계속 검토해야 할 UI 오류"로 남겨달라고 명시해 등록한다.

## 원인 후보 (우선순위순)

1. **(유력) 아직 배포 안 됨.** 0034가 `main`에 로컬 커밋만 있고 push·재배포 전이라, 지금
   `law-rag-web.vercel.app`은 여전히 예전 코드(모든 `SIGNED_IN` 이벤트에 무조건
   `hydrateUser()` 호출)를 쓰고 있을 가능성이 크다.
2. **(설계상 정상일 수 있음) 60초 throttle 자체.** 0034는 재호출을 완전히 막은 게
   아니라 `HYDRATE_THROTTLE_MS = 60_000`([page.tsx:85](../../../apps/web/app/page.tsx:85))
   안에서만 억제한다 - 60초 넘게 텀을 두고 탭을 오가면 다시 호출되는 게 **의도된
   동작**이다. 사용자가 "여전히 계속 호출된다"고 느낀 게 60초 이내 재호출(버그)인지,
   60초 넘겨서마다 한 번씩(설계상 정상)인지 구분이 안 된 상태다.
3. **(가능성 낮음, 배제 필요) 다른 호출 경로.** grep으로 `/v1/auth/me`를 부르는 코드가
   `hydrateUser()` 하나뿐임을 확인했다 - 숨은 타이머·폴링은 현재 없다. 이 결론은 배포된
   빌드가 아니라 현재 로컬 소스 기준이라, 배포본이 다른 커밋일 경우 다시 확인해야 한다.

## 설계 (미착수, 방향만)

- 먼저 0034를 `git push`하고 실제로 배포한 뒤, 배포된 사이트에서 재현되는지부터 다시
  확인한다 - 이게 안 되면 이후 항목은 의미가 없다.
- 배포 후에도 재현되면: 60초 이내 재호출인지(진짜 버그, throttle 로직 자체를 다시 조사)
  vs 60초 넘겨서 한 번씩인지(설계 값 자체가 사용자 기대와 안 맞는 것 - "탭 전환으로는
  아예 재호출하지 말아야 한다"는 요구라면 `HYDRATE_THROTTLE_MS`를 늘리거나
  `SIGNED_IN`을 아예 무시하는 방향까지 재검토)를 구분해서 원인을 좁힌다.
- Supabase JS SDK 버전에 따라 탭 재포커스 시 실제로 어떤 이벤트를 얼마나 자주 쏘는지
  (SIGNED_IN 재발생 빈도)도 실측이 필요할 수 있다 - 지금까지는 코드 주석 수준의 추정이다.

## 비범위

- 0034 자체의 재구현(이미 완료·커밋됨)은 이번 항목이 아니다 - 이건 그 결과를 배포 후
  검증하는 후속 항목이다.

## 승격 조건

- 0034가 실제로 배포된 뒤 사용자가 재확인을 요청한다.

## 완료 조건

- 배포된 사이트에서 로그인 상태로 탭을 반복 전환했을 때(60초 이내) `/v1/auth/me` 추가
  호출이 없다.
- 60초를 넘긴 재포커스에서의 재호출이 사용자 기대와 일치하는지(허용/비허용) 확정되고,
  필요하면 `HYDRATE_THROTTLE_MS` 값이나 로직이 그에 맞게 조정된다.
