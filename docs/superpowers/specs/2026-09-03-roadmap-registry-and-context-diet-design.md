# 로드맵 정본·컨텍스트 절약 설계

## 목적

실행계획의 상태·다음 행동·참조 범위를 한 곳에서 관리하고, `docs/ROADMAP.md`는 그 메타데이터로부터 항상 재생성한다. 에이전트는 시작 시 얇은 색인과 선택한 작업의 명시된 줄 범위만 읽어, 불필요한 계획 본문·완료 이력·코드 복제로 인한 토큰 사용을 피한다.

## 현재 구조와 용어

로드맵은 Epic → Story → Task 트리가 아니라 **단일 milestone(작업) 목록**이다. 각 milestone은 다음 유형 중 하나다.

- `Feature` (`F-*`)
- `Bug` (`B-*`)
- `Tech Debt` (`TD-*`)
- `Experiment` (`E-*`)
- `Operations` (`O-*`)
- `Documentation` (`DOC-*`)

`D-*`는 기존 기록의 역사적 ID로만 유지한다. 상위 Epic 유형이나 별도 계층은 추가하지 않는다. 여러 milestone을 묶어 설명할 필요가 있으면 상위 Feature의 본문에서 관계를 설명하되, roadmap의 단일 목록·유일 `Picked Up` 규칙은 바꾸지 않는다.

## 권위 관계

```text
실행계획 파일의 상단 메타데이터 (유일한 정본)
  ├─ render_roadmap.py → docs/ROADMAP.md (생성물)
  ├─ check_roadmap.py  → 상태·위치·참조·생성 결과 검사
  └─ roadmap-operator skill → 필요한 범위만 읽고 상태 전이를 수행
```

`docs/ROADMAP.md`와 `docs/exec-plans/*/README.md`는 정본이 아니다. ROADMAP은 직접 편집하지 않는다. 상태·제목·다음 행동의 변경은 먼저 해당 실행계획의 상단 메타데이터에 기록하고, 재생성한다.

## 실행계획 색인 헤더

새 실행계획과 상태가 전이되는 실행계획은 파일 시작부터 첫 `##` 헤딩 직전까지를 색인 헤더로 둔다. 기존 여섯 필드에 `다음 행동`을 추가한다.

```md
> 작업 ID: `F-001`
> 상태: `Todo`
> 유형: `Feature`
> 보조 라벨: `Data`, `Evaluation`
> 선행 조건: 없음
> 다음 행동: 요구사항별 API 계약 회귀 테스트부터 시작
> 참고 범위:
> - `apps/api/app/history.py` L42-L118 — 현재 이력 경계
```

- 제목은 H1, 계획 번호는 파일명에서 얻는다. 이 값을 메타데이터에 중복하지 않는다.
- `다음 행동`은 한 문장이고 120자를 넘지 않는다.
- `참고 범위`는 최대 3개다. 각 항목은 저장소 상대 경로, 시작·끝 줄, 읽는 이유를 반드시 가진다.
- 색인 헤더에는 코드 블록, 구현 절차, 테스트 출력, 장문의 배경 설명을 넣지 않는다.
- 계획 본문도 코드를 복제하는 대신 경로·줄 범위·안정적인 섹션 앵커를 우선한다. 코드가 그 자체로 계약인 경우만 최소 예시를 허용한다.

## 상태와 파일 lifecycle

상태는 `Todo`, `Picked Up`, `Blocked`, `Done`만 허용한다. 전체 저장소에서 `Picked Up`은 0개 또는 1개다. 계획 artifact는 `todo/`, `active/`, `completed/`에 보관하며, 상태 전이 때도 같은 파일명과 계획 번호를 유지한다.

- `todo/`: 새 제안 또는 미착수 계획
- `active/`: 진행 기록이 있는 계획. 다음 milestone이 시작 전이면 `Todo`일 수 있다.
- `completed/`: 완료 검증과 결과·잔여 작업 기록까지 끝난 `Done` 계획

파일 위치와 상태의 허용 조합은 기존 `docs/PLANS.md` 계약을 보존한다. 이 설계는 lifecycle을 바꾸지 않고 정본을 기계적으로 읽을 수 있게 한다.

## 생성되는 로드맵

생성기는 각 계획의 색인 헤더만 파싱해 `Todo`, `Blocked`, `Done` 섹션을 렌더한다. 각 행은 작업 ID, 유형, 계획 제목 링크, `다음 행동` 또는 `재개 조건`만 가진다. `Done`은 최신 12개만 보여주고 완료 계획 색인으로 연결한다.

파일 상단에는 생성 명령과 모든 입력 메타데이터에 대한 안정적인 digest를 주석으로 기록한다. 현재 시각 같은 변동 값은 쓰지 않는다. 따라서 Git diff는 실제 실행계획 메타데이터 변화에 의한 로드맵 변화만 보인다.

## 최소 읽기 계약

`roadmap-operator`는 다음 순서를 강제한다.

1. 시작 컨텍스트로 `docs/CURRENT_STATE.md` L1-L28과 `docs/ROADMAP.md`의 시작부터 마지막 비완료 행까지만 읽는다.
2. 선택한 작업은 실행계획 파일의 시작부터 첫 `##` 직전까지만 읽는다.
3. 이어서 그 헤더의 `참고 범위`에 적힌 각 파일의 명시된 `L시작-L끝`만 읽는다.
4. 범위 밖 문맥이 반드시 필요하면, 추가할 경로·시작줄·끝줄·이유를 먼저 사용자에게 또는 작업 기록에 명시한다.

다른 실행계획의 본문, 완료 계획 전체, 아키텍처·설계 문서 전체는 위 범위만으로 부족할 때만 읽는다. 스킬은 상태 전이 전후에 읽은 범위를 짧게 보고한다.

## 검사와 훅

`scripts/check_roadmap.py`는 다음을 검사한다.

- 필수 색인 필드와 허용된 상태·유형·라벨
- 작업 ID 중복 없음
- `Picked Up` 0개 또는 1개
- 파일 위치와 상태 lifecycle의 허용 조합
- 참고 범위의 형식, 경로 존재, 유효한 줄 범위
- 생성한 roadmap과 저장소의 `docs/ROADMAP.md`가 완전히 일치함

검사는 파일을 바꾸지 않는다. `scripts/render_roadmap.py`만 roadmap을 재생성한다. 이 구분은 commit 전에 staged index가 예상치 않게 변하는 일을 막고, 오류 원인을 원본 계획 메타데이터로 돌려준다.

프로젝트 설치 스크립트가 `.git/hooks/pre-commit`에 로드맵 검사 훅을 설치한다. staged 변경이 `docs/exec-plans/**` 또는 `docs/ROADMAP.md`를 포함할 때만 `check_roadmap.py --staged`를 실행하고, 그 외에는 즉시 종료한다. 기존 개인 `post-commit` graphify 훅을 교체하거나 `core.hooksPath`를 변경하지 않는다. CI는 같은 검사를 항상 실행한다.

## 오류 처리와 관측성

검사 실패에는 작업 ID·파일·필드와 정확한 수정 명령을 표시한다. 렌더 불일치는 첫 차이와 `render_roadmap.py` 실행 방법을 표시한다. 성공 시에는 파싱한 계획 수, `Picked Up` 수, roadmap digest만 출력한다. 계획 본문·개인 데이터·전체 문서는 출력하지 않는다.

## 검증

- 유효한 최소 메타데이터에서 결정적 roadmap을 생성한다.
- ID 중복, 두 개의 `Picked Up`, 잘못된 상태/위치, 잘못된 줄 범위, 수동 수정 roadmap을 각각 실패시킨다.
- 계획 관련 파일이 staged일 때만 pre-commit이 검사를 호출한다.
- CI에서 문서 검사와 roadmap 검사가 통과한다.

## 비범위

- GitHub Project와 저장소 roadmap의 자동 동기화
- Epic, Story, Task 계층 도입
- 기존 완료 계획 전체의 일괄 메타데이터 이행
- 훅이 파일을 자동 수정하거나 commit을 자동 생성하는 동작
