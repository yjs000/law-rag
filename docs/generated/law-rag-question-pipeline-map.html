사전 라우팅 (tier1 → tier2)

규칙 기반 tier1이 외부 문서 요구·실시간성·개인 상태·조건부 변동 문구를 먼저 판단한다. 규칙으로 확정하지 못한 질문만 tier2가 NVIDIA NIM에 구조화 분류를 요청한다.

검색 — 5단계, 매칭되면 즉시 반환

각 단계는 자체 SQL의 WHERE절에서 기준일 유효 버전만 이미 걸러서 조회한다(효력 시작일 이전·종료일 이후 버전은 애초에 후보에 안 들어옴) — 전체 코퍼스를 긁은 뒤 나중에 자르는 게 아니다.

0. 조문경로 직접 조회 — 질문 텍스트에 "제N조" 류 패턴이 있을 때만(법령명 없어도 트리거됨). 한번 이 분기를 타면 조회 결과가 비어도 절대 아래 1~4단계로 안 내려간다 — 그 질문은 그대로 근거 0건으로 끝난다.

1. 벡터(밀집) 검색 — 임베딩이 있을 때만 시도, 후보가 하나라도 있으면 즉시 반환.

2~4. 키워드 검색, 3단 완화 — 전체어 일치(질문어 전부 매칭) → 실패 시 최소 2어 일치로 후보 풀을 넓힘 → 그 풀 안에서 앵커어(법령명·에너지 도메인 핵심어) 포함분만 최종 채택, 없으면 앵커 쿼리를 새로 실행. 각 단계는 이전 단계가 빈손일 때만 실행되고, 벡터(dense) 결과가 이미 있으면 이 체인 전체를 건너뛴다. 도입 배경·dense-only 제한 배경은 결정 기록(2026-07-18, 2026-08-03) 참고.

생성용 근거 선정

검색이 준 순서(재순위 없음) 그대로 훑으면서 3가지를 동시에 적용한다.

중복 판단: hit.path의 첫 "/" 앞부분을 "조"로 본다("제7조/항①" → "제7조"). (문서 ID, 조) 조합이 이미 나왔으면 그 항·호·목 청크는 건너뛴다 — 한 조당 최대 1개.

인용 ID가 실제 제공된 근거를 가리키는지, action별 필수 필드가 채워졌는지만 본다. 문장 내용이 근거와 의미적으로 겹치는지는 더 이상 이 구조 검증기가 판단하지 않는다(축소 배경은 결정 기록(2026-08-08) 참고) — 관련 근거를 고르는 책임은 검색·재순위 쪽으로 넘어갔다.

0046의 빈 근거 검증: hits가 비어 있으면 sections·checklist가 모두 비어 있는 unanswerable, 또는 missing_information이 있는 clarification_required만 통과한다. 다른 action이나 내용이 든 sections·checklist는 거부해 근거 없는 법적 주장을 막는다.

clarification_required는 두 경로에서 생성될 수 있다. 검색 전 route에서는 전용 프롬프트가 필요한 사실을 만들고, 검색 후 action에서는 근거를 본 생성 모델이 필요한 사실을 낸다. 두 경우 모두 main.py가 기존 재제출 템플릿으로 정리한다. route는 검색 실행 판단, action은 생성 답변 완결성이라 서로 덮어쓰지 않는다.

생성 또는 구조 검증이 실패하면 검색 경로는 미리 만든 search_only 폴백을, 사전 차단 경로는 기존 차단 안내문을 반환한다.

응답 조립 · 저장

Citation: generation_hits(04단계에서 예산 안으로 추려진 것, 검색된 전체가 아님)를 1번부터 순서대로 C1, C2...로 번호 매겨 만든다. 이제 source_kind(law/administrative_rule)와 law_type_code(법률·시행령·시행규칙 등의 Open API 분류 코드)를 둘 다 싣는다.

limitations: 모델이 낸 draft.limitations 뒤에 고정 문구("이 서비스는 법률 자문을 대체하지 않습니다")를 항상 덧붙인다.

corpus_as_of: repository.last_sync() — 코퍼스가 마지막으로 갱신된 시각.

route는 검색 전 라우터가 정한 처리 경로다: 법령 검색을 진행할지(legal_search), 먼저 사실을 물을지, 실시간 정보·외부 문서가 필요한지 나타낸다. action은 검색·생성 후 모델이 구조화 출력으로 밝힌 답변 완결성이다: 완전 답변, 부분 답변, 추가 사실 필요, 근거로 답변 불가를 나타낸다. 둘은 서로 다른 시점과 질문을 표현하므로 하나로 재계산하거나 덮어쓰지 않는다.

왜 그대로 옮기나: route를 응답 조립 단계에서 다시 추론하면 이미 실행한 경로와 diagnostics가 달라질 수 있고, action을 checklist나 summary 문구에서 다시 추측하면 과거 grounding 오탐을 되살린다. 따라서 검증을 통과한 원래 결정 신호를 보존해 프런트·이력·후속 calibration이 “어디서 왜 분기됐는지” 추적하게 한다. 다만 생성 후 clarification은 위 설명처럼 route=legal_search, action=clarification_required의 두 축을 의도적으로 함께 가진다.

저장은 로그인 + 약관 동의한 사용자에 한해서만 대화 이력에 남긴다.
