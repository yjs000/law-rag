# Dropped 수명주기와 병렬 오케스트레이션

상태: 승인 (2026-09-17)

## 목적

실행하지 않기로 결정한 계획을 완료로 위장하거나 삭제하지 않고 `Dropped`로 보존한다. 구현 준비가
끝난 비실험 작업은 `OC-001` 하나가 우선순위, 선행 작업, 파일 소유 범위와 실행 상태를 추적하며,
서로 충돌하지 않는 작업을 독립 worktree에서 병렬 실행한다.

이 설계는 기존 실행계획 헤더를 정본으로 유지한다. `docs/ROADMAP.md`는 헤더에서 생성되는 얇은
색인이며 상태나 오케스트레이션 목록을 직접 편집하지 않는다.

## 적용 범위

- `Dropped` 상태와 `docs/exec-plans/dropped/` lifecycle 디렉터리
- `Orchestration` 유형과 `OC-NNN` 작업 ID
- 실행계획 헤더의 오케스트레이션 메타데이터
- `scripts/roadmap_registry.py`, renderer, checker와 해당 테스트
- `OC-001`과 그 여섯 자식 계획의 초기 상태
- `roadmap-operator`, `docs/PLANS.md`, `AGENTS.md`의 운영 계약

다음은 범위 밖이다.

- Dropped 계획과 관련해 이미 존재하는 구현 코드 삭제 또는 롤백
- `B-009` 구현·조사·상태 변경
- `B-001`, `B-002`, `F-002` 구체화 또는 현재 구현 감사
- 모든 `Experiment` 작업
- 외부 서비스, 데이터베이스, 배포, GitHub Issue 또는 원격 branch 변경
- OC executor를 별도 상주 서비스나 scheduler로 구현하는 일

## Dropped 수명주기

`Dropped`는 사용자가 더 이상 실행하지 않기로 결정한 계획이다. 구현과 검증을 완료했다는 뜻이
아니므로 `Done`과 구분한다.

- Dropped 계획은 `docs/exec-plans/dropped/`에 둔다.
- 헤더의 `상태`는 `Dropped`이고 `폐기 사유`를 반드시 가진다.
- `다음 행동`은 `없음.`으로 유지해 기존 색인 문법과 한 문장 계약을 지킨다.
- ROADMAP의 `Dropped` 절에는 작업 ID, 유형, 제목, 폐기 사유와 계획 링크를 표시한다.
- Dropped 계획은 `Picked Up`, `Todo`, `Blocked`, `Done` 집계에 포함하지 않는다.
- Dropped 계획을 되살릴 때는 사용자가 명시적으로 승인한 새 실행계획을 만든다. 기존 계획의 상태를
  소급해 `Todo`로 되돌리지 않는다.

초기 Dropped 전이는 다음 세 계획에만 적용한다.

| 작업 | 폐기 사유 | 기존 코드 처리 |
| --- | --- | --- |
| `F-001` | 사용자가 V3를 아직 진행하지 않기로 결정 | Task 1~11의 기존 구현과 commit은 유지 |
| `F-003` | 사용자가 라이브 검색 재순위를 진행하지 않기로 결정 | 오프라인 실험 코드는 유지 |
| `F-004` | 사용자가 provider 중립 모델 선택 계약을 진행하지 않기로 결정 | 현재 `terra` 호환 계약 유지 |

## OC 메타데이터 계약

`Orchestration` 계획은 `OC-NNN` ID를 사용한다. `OC-001`만 최상위 `Picked Up`이며 자식 계획은
`Todo` 상태로 `active/`에 위치한다. 자식의 실제 실행 상태는 `관리 상태`가 나타낸다.

OC 자식 헤더에는 다음 필드를 추가한다.

```md
> 오케스트레이션: `OC-001`
> 우선순위: `P0`
> 관리 상태: `준비 중`
> 선행 작업: 없음
> 소유 범위:
> - `apps/api/app/domain/corpus_temporal_contract.py`
> - `apps/api/app/api/v2/search.py`
```

- `우선순위`는 `P0`, `P1`, `P2`, `P3` 중 하나다.
- `관리 상태`는 `대기`, `준비 중`, `실행 중`, `통합 대기`, `검증 중` 중 하나다.
- `선행 작업`은 쉼표로 구분한 작업 ID 또는 `없음`이다.
- `소유 범위`는 저장소 상대 파일 경로 또는 디렉터리 접두사다. glob과 상위 경로 `..`는 허용하지
  않는다.
- 일반 계획에는 OC 필드가 없어도 된다. 실행 중인 OC 자식은 필드 중 하나가 있으면 모든 OC 필드가 필요하다.
- 완료된 자식은 부모 `오케스트레이션` 연결만 남기고 실행용 OC 필드를 제거한 뒤 기존 계약대로 `Done`으로
  바꾸고 `completed/`로 이동한다.

## OC-001 범위와 제외

`OC-001`은 구현 준비도가 확인된 다음 여섯 작업만 관리한다.

| 우선순위 | 작업 | 역할 | 초기 선행 작업 |
| --- | --- | --- | --- |
| P0 | `B-003` | V2 KST today 상한 | 없음 |
| P0 | `B-008` | 내부 라우팅 문구 비노출 | 없음 |
| P0 | `B-010` | 한 글자 질문 허용 | `B-003`, `B-008` |
| P1 | `F-007` | 체크리스트 내보내기 제거 | P0 묶음 완료 |
| P1 | `F-009` | NVIDIA 지연 안내와 상단 진행 표시 | `F-007` |
| P1 | `F-010` | 쉬운 한국어 프롬프트 | P0 묶음 완료 |

다음 작업은 OC-001에 속하지 않는다.

- `B-009`: 사용자가 현재 구현을 직접 확인한 뒤 진행 여부와 범위를 정한다.
- `B-001`, `B-002`, `F-002`: 현재 구현 감사와 구체화가 먼저 필요하다.
- `F-001`, `F-003`, `F-004`: Dropped 처리한다.
- 모든 `E-*`: 실험은 이번 오케스트레이션에서 제외한다.

P0 묶음 완료처럼 여러 ID를 뜻하는 표현은 저장 메타데이터에는 쓰지 않는다. `F-007`과 `F-010`의
`선행 작업`에는 `B-003`, `B-008`, `B-010`을 명시한다.

## 병렬 실행과 파일 소유

OC executor는 준비된 작업 중 가장 높은 우선순위부터 선택하고, 소유 범위가 겹치지 않는 최대 세 작업을
독립 worktree와 독립 branch에서 병렬 실행한다. 현재 Codex 동시성 네 슬롯 중 하나는 OC 통합 담당자가
보유한다.

초기 실행 파동은 다음과 같다.

1. `B-003`과 `B-008`을 병렬 실행한다.
2. 두 작업을 기준 branch에 통합하고 검증한 뒤 `B-010`을 실행한다.
3. P0 통합 검증 뒤 `F-007`과 `F-010`을 병렬 실행한다.
4. `F-007` 통합 뒤 `F-009`를 실행한다.
5. 여섯 자식이 모두 Done이면 OC 전체 검증을 실행한다.

공유 파일은 자식 소유 범위에서 제외하고 OC 통합 담당자만 수정한다.

- `docs/ROADMAP.md`
- OC 및 자식 실행계획 헤더·위치
- 여러 자식이 함께 바꾸는 제품 명세 또는 운영 문서
- 병렬 계획에서 겹치는 테스트 파일

checker는 두 `실행 중` 자식의 정규화된 소유 범위가 같거나 한 범위가 다른 범위의 디렉터리 접두사이면
오류로 처리한다. `준비 중` 작업끼리 겹치는 것은 허용하며 OC executor가 같은 wave에 배치하지 않는다.

## 상태 전이와 완료 판정

OC executor는 다음 상태 전이를 사용한다.

1. 선행 작업이 모두 Done이면 `대기`에서 `준비 중`으로 전환한다.
2. worktree와 담당 agent가 배정되면 `실행 중`으로 전환한다.
3. child branch가 focused 검증과 리뷰를 통과하면 `통합 대기`로 전환한다.
4. 기준 branch에 반영되면 `검증 중`으로 전환한다.
5. 통합 후 관련 검증이 통과하면 child를 `Done`으로 전환하고 `completed/`로 이동한다.

renderer와 checker는 테스트 명령을 실행하거나 상태를 자동 변경하지 않는다. checker는 구조적 준비도와
상태 불변조건만 검증한다. 실제 완료 판정은 OC 통합 담당자가 최신 테스트 출력과 diff를 확인한 뒤
헤더를 전이하는 방식으로 유지한다.

`OC-001`은 다음 조건을 모두 충족할 때만 Done이다.

- 여섯 자식 계획이 모두 `Done`이고 `completed/`에 있다.
- 관리 상태가 남은 자식이 없다.
- OC 계획에 각 자식 commit과 통합 순서가 기록돼 있다.
- roadmap checker, 문서 검사, 관련 Python/Web 전체 검증이 최신 실행에서 통과했다.
- 미통합 child worktree 결과가 없다.

남은 자식이 모두 외부 입력을 기다리면 OC를 `Blocked`로 전환한다. 준비된 자식이 하나라도 있으면 다른
자식의 차단 때문에 OC 전체를 막지 않는다.

## 생성과 검증 계약

renderer는 기존 최상위 절에 `Dropped`를 추가하고, `Picked Up`이 Orchestration 유형이면 그 아래에
자식 관리 표를 생성한다. 같은 자식은 일반 `Todo` 절에 중복 표시하지 않는다.

checker는 기존 검증에 다음을 추가한다.

- `Dropped` 상태와 `dropped/` 위치의 양방향 lifecycle 일치
- Dropped 계획의 폐기 사유 존재
- `OC-NNN` ID와 `Orchestration` 유형 일치
- OC 부모 ID 존재 및 상태가 `Picked Up` 또는 `Blocked`인지 확인
- OC 필드의 완전성, 허용 우선순위와 관리 상태
- 선행 작업 ID 존재, 자기 의존과 순환 의존 금지
- `준비 중` 이상 자식의 선행 작업 Done 확인
- 동시에 `실행 중`인 자식의 소유 범위 비중첩
- Done/Dropped 자식에 관리 상태가 남지 않음
- OC Done 시 모든 자식 Done
- staged 검사에서도 같은 규칙 적용

## 검증 전략

- registry 단위 테스트는 Dropped lifecycle, OC 필드 파싱, 의존성 그래프와 소유 범위 충돌을 RED로 먼저
  고정한다.
- renderer 테스트는 Dropped 절과 OC 관리 표, Todo 중복 제거를 검증한다.
- checker의 worktree/staged 모드는 동일한 결과를 내야 한다.
- 실제 계획 전이 뒤 roadmap renderer와 checker, 문서 검사, `git diff --check`를 실행한다.
- 구현 완료 시 `scripts/verify.ps1` 전체 검증을 실행한다.
