01 · 전체 구조와 v2 실행 단계

웹 질문 transport는 v2 execution API를 사용한다. v1 API도 남아 있다. v2는 프로젝트 서비스가 prepare → core → finalize를 조정한다.

02 · RouteDecision을 먼저 확인하는 이유

QuestionRouter는 판정 인터페이스, NvidiaNimQuestionRouter는 직접 NVIDIA NIM을 호출하는 구현체, RouteDecision은 판정 결과다. v1/v2가 같은 구현 클래스를 별도 인스턴스로 사용한다. LlamaIndex Router가 아니다.

HTTP 앞 단계

Workflow 활성 + 새 질문이면
_prepare_clarification_turn에서 router 호출

→
PrepareQuestion

계산한 route_decision을 내부 인자로 전달
클라이언트가 route를 지정하는 기능이 아님

→
서비스 _route

terra 외 모드 → legal_search
판정 있음 → 재사용
판정 없음 → router 호출

같은 요청에서 LLM을 두 번 호출하지 않기 위한 재사용이다. 이전 답변의 판정을 캐시하는 분기가 아니다. 후속 case 요청은 앞 단계의 최초 라우터를 건너뛰지만, 서비스에는 RouteDecision이 전달되지 않아 terra 모드에서 현재 문장으로 router를 다시 호출한다.
legal_search

Workflow 비활성이면 앞 단계는 판정하지 않고 서비스에서 router를 호출한다. 서비스 _route는 terra 외 모드에서 전달된 판정보다 legal_search를 우선한다.

03 · 추가 질문: 한 턴의 Workflow와 여러 턴의 case

Context는 턴마다 새로 만든다. 다음 HTTP 요청이 같은 clarification_case_id로 저장된 case를 읽어 대화를 이어간다.

첫 질문

router → clarification_required → 초기 judge가 필요한 사실 후보 추출 → 서버 fact ID 부여 → case 생성.

후속 질문

case ID + 사용자 문장 → 소유권·capability·만료 확인 → 원 질문과 미해결 facts로 continuation extractor 호출 → 검증한 fact 병합.

취소·새 질문 의도는 기존 case를 cancelled로 만든다. 만료 상태는 expired. interpreter 실패는 interim 안전 오류 결과로 종료한다. policy는 상태 판단이며 full/conditional이 정상 답변 성공을 보장하지는 않는다.

현재 연결의 빈틈 · B-016 / B-014 / B-009
후속 fact 추출에는 원 질문을 사용하지만 이후 검색은 현재 요청 문장을 사용한다. 답변용 snapshot에는 누적 fact 값이 없다. Outcome policy가 서비스 route를 자동으로 legal_search로 바꾸지도 않는다. 따라서 “모든 사실 입력 → 원 질문에 적용한 최종 답변”이 완성됐다고 표시하지 않는다.

  • case 상태·저장소

  • B-016 원 질문·누적 사실 입력
