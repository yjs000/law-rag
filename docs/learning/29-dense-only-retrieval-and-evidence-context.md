# Dense-only 검색과 근거 문맥의 경계

확인일: 2026-08-03

## 한 문장 결론

현재 시스템은 임베딩 검색과 키워드 검색의 점수를 섞지 않는다. 임베딩이 준비된 일반 질문은 dense-only로 검색하고, 결과가 하나도 없을 때만 키워드 검색을 별도 안전 경로로 실행한다.

## 검색 방식 세 가지를 구분하기

### Dense retrieval

질문과 문서 조각을 같은 임베딩 모델의 벡터로 바꾸고, 벡터 방향이 가까운 순서로 문서를 찾는 방식이다. 표현이 달라도 의미가 비슷한 문장을 찾는 데 유리하다.

현재 계약은 다음과 같다.

- 모델: `nvidia/nemotron-3-embed-1b`
- NIM 반환값: 2048차원
- 저장·검색값: 앞 512차원을 유지한 뒤 L2 재정규화
- embedding version: `1`
- 질문과 문서에 같은 모델·차원 축약·정규화를 사용

### Keyword retrieval

질문에 실제로 포함된 단어가 법률명·표제·본문에 나타나는지 찾는 방식이다. 법률명, 조문 번호, 전문용어처럼 정확한 표현에 강하다. 현재 키워드 경로는 모든 핵심어 일치부터 시작하고, 최소 두 단어와 도메인 앵커를 요구하는 단계로만 완화한다.

### Hybrid retrieval

한 질문에 dense와 keyword 검색을 둘 다 수행한 뒤 두 결과를 하나의 순위로 합치는 방식이다. 점수 합산, 가중 평균, RRF 같은 결합 규칙이 필요하다.

현재 시스템은 hybrid를 사용하지 않는다. 데이터와 질문이 더 다양한 평가셋에서 dense-only보다 직접 근거를 실제로 개선하는지 확인하기 전에는 복잡도를 추가하지 않기로 결정했다.

## 폴백은 왜 hybrid가 아닌가

현재 흐름은 다음과 같다.

```text
dense 검색
├─ 결과 있음: dense 순위만 반환
└─ 결과 0개: keyword 검색을 새로 실행해 그 순위만 반환
```

두 점수가 한 후보에 동시에 영향을 주지 않는다. 어느 한 번의 응답은 dense 결과이거나 keyword 결과일 뿐이다. 따라서 이는 검색 방식의 결합이 아니라 실패 시 실행 경로를 바꾸는 폴백이다.

## RRF는 무엇이며 왜 지금 사용하지 않는가

RRF는 Reciprocal Rank Fusion, 즉 여러 검색 결과의 순위를 이용해 하나의 순위를 만드는 방법이다. 서로 단위가 다른 dense 점수와 keyword 점수를 직접 더하지 않고, 각 검색에서 몇 위였는지를 사용한다.

```text
RRF(document) = Σ 1 / (k + rank)
```

두 검색에서 모두 높은 문서는 최종 순위도 높아진다. 그러나 결합 규칙을 추가했다는 사실만으로 검색이 좋아지는 것은 아니다. 현재 고정 실험에서 corpus와 법률 계층을 고친 dense-only가 범위 내 기대 근거를 모두 1위에서 찾았으므로, RRF가 개선할 수 있다는 증거가 아직 없다. RRF는 더 어려운 평가 질문을 추가한 뒤 별도 비교한다.

## 청크 후보와 조문 후보

파서는 조·항·호·목을 각각 검색 가능한 작은 단위로 저장한다. 작은 단위는 질문과 직접 맞는 문장을 찾기 좋지만, 같은 조의 여러 하위 단위가 상위 순위를 독점할 수 있다.

예를 들어 검색 결과가 다음과 같을 수 있다.

```text
1위 제7조/항①
2위 제7조/항②
3위 제7조/항①/호1.
4위 제8조
```

답변 후보로는 제7조가 세 번 필요한 것이 아니다. 현재 검색은 문서 ID와 조문 루트를 기준으로 묶어 각 조에서 가장 높은 청크 하나만 남긴다.

```text
1위 제7조의 대표 청크
2위 제8조의 대표 청크
```

이 동작은 AI 재순위가 아니다. 이미 계산된 순서를 유지하면서 같은 조의 중복만 결정적으로 제거한다.

## 후보 10개와 생성 문맥 5개의 차이

검색 후보는 필요한 근거를 놓치지 않기 위해 비교적 넉넉하게 본다. 답변 모델에는 그 후보를 모두 넣지 않고, 순위가 높은 서로 다른 조문을 최대 5개까지만 문자 예산 안에서 전달한다.

- 후보 검색: 근거 누락을 줄이는 단계
- 조 단위 중복 제거: 같은 조가 문맥을 독점하지 않게 하는 단계
- 생성 문맥 제한: 무관한 내용과 입력 비용을 줄이는 단계

`5`가 법률 RAG의 보편적 정답이라는 뜻은 아니다. 현재의 보수적 상한이며, 이후 고정 평가셋에서 직접 근거를 놓치면 다시 조정해야 한다.

## Evidence Recall은 런타임 검색 단계가 아니다

Evidence Recall은 정답 근거를 미리 표시한 평가 질문에서 검색 후보가 그 근거를 얼마나 놓치지 않았는지 측정하는 오프라인 지표다.

```text
Evidence Recall@3
= 상위 3개 안에 정답 근거가 들어온 질문 수 / 전체 평가 질문 수
```

새로운 사용자 질문에서는 정답을 아직 모르기 때문에 이 값을 즉시 계산할 수 없다. 따라서 프로덕션 요청마다 Evidence Recall을 검사하는 단계는 없다. 프로덕션 검색이나 프롬프트를 바꾼 뒤, 정답이 표시된 고정 평가셋을 다시 실행해 회귀 여부를 확인하는 용도다.

## 점수가 높은데도 근거가 아닐 수 있는 이유

코사인 유사도는 질문 벡터와 문서 벡터의 방향이 얼마나 가까운지를 나타낸다. 정답 확률도 아니고, 법적 요건을 직접 뒷받침한다는 보증도 아니다.

질문이 “전기사업 허가권자는 누구인가?”일 때 다음 문장은 주제는 가깝지만 직접 답하지 않는다.

```text
제7조에 따라 허가받은 자
```

다음 문장은 답을 직접 포함한다.

```text
전기사업을 하려는 자는 산업통상자원부장관의 허가를 받아야 한다.
```

그래서 현재 구현은 임의 similarity cutoff를 정답 판정기로 사용하지 않는다. 범용 `insufficient_evidence`를 만들려면 질문의 필수 답변 요소와 원문이 직접 대응하는지 평가하는 별도의 근거 선택기, 실패 계약, 고정 평가셋이 먼저 필요하다.

## 현재 확정된 구현과 보류 항목

현재 확정:

- Open API 원문만 수집
- 구조 표지와 실제 조문 본문 구분
- 조·항·호·목의 부모 경로 검증
- direct path 검색 우선
- NVIDIA 512차원 dense-only 검색
- dense 0건일 때 독립 keyword fallback
- 조 단위 중복 제거
- 생성 문맥 최대 5개 조문
- Evidence Recall과 고정 필수 문구는 오프라인 실험에서만 사용

후속 실험:

- BM25 또는 다른 lexical 검색기
- dense+lexical hybrid
- RRF
- 모델 기반 reranker
- 범용 직접 근거 선택기와 `insufficient_evidence` 게이트

설계의 권위 문서는 [RAG 파이프라인 설계](../design-docs/rag-pipeline.md)와 [근거 우선 검색 품질 설계](../design-docs/evidence-first-retrieval-quality.md)다.
