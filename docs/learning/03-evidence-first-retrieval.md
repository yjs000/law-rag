# 3. 근거 우선 검색과 답변

## RAG의 목적은 그럴듯한 문장이 아니다

RAG는 질문에 답하기 전에 외부 문서에서 근거를 검색해 생성 모델에 제공하는 방식이다. 법률 RAG에서
검색은 단순한 참고 기능이 아니다. 실질 주장, 의무, 예외, 숫자와 체크리스트가 어떤 원문·버전·조문
위치에서 왔는지 제한하는 안전 경계다.

```text
질문
→ 입력·기준일·코퍼스 gate
→ 직접 경로 또는 자연어 검색
→ 후보와 답변 문맥 구성
→ 구조화 답변 초안
→ 결정적 인용 gate
→ 답변 또는 검색 전용 폴백
```

검색에 실패했는데 모델 기억으로 법률을 채우지 않는다. 근거가 없으면 그 상태를 보여 주고 생성을
중단한다.

## 먼저 구조 질의와 자연어 질의를 나눈다

`전기사업법 제7조 제1항`처럼 사용자가 원문 위치를 말한 질문은 의미 검색보다 직접 경로 조회가
정확하다. 입력 표기를 정규 경로로 바꾸고, Open API 원문의 원형 숫자·기호 경로도 같은 위치로
취급한다.

- `1조2항`, `제일조 제이항` → `제1조/항2`
- `제1조 제2항 및 제3항` → 같은 조의 두 경로
- `제1조부터 제3조` → 요청 순서를 보존한 세 경로
- 법령명이 있으면 그 법령만, 없으면 허용 코퍼스 전체의 같은 경로

범위는 최대 20개 조다. 역방향이나 초과 범위는 일부만 반환하거나 일반 검색으로 우회하지 않는다.
요청과 다른 조문이 “가까운 결과”로 섞이면 직접 조회의 의미가 사라지기 때문이다.

경로가 없으면 `result_status=no_results`와 `requested_path_not_found`를 반환한다. 일반 자연어 검색에서
안전한 후보가 없으면 `no_matching_evidence`다. 두 경우 모두 HTTP 요청 자체는 성공했지만 사용자가
확인할 근거가 없다는 뜻이다. 저장소 장애나 닫힌 코퍼스와는 다르다.

## 자연어 검색의 현재 경로

현재 일반 질문의 주 검색은 dense-only다. 질문 임베딩을 만들 수 있고 현재 profile의 문서 벡터가
준비됐다면 기준일에 유효한 모든 대상 벡터와 exact cosine으로 비교한다. dense 후보가 하나라도 있으면
그 순위만 사용한다.

임베딩 경로가 없거나 dense 후보가 0개일 때만 PGroonga keyword 검색을 독립적으로 실행한다.

```text
dense 검색
├─ 후보 있음 → dense 결과
└─ 후보 없음/embedding 없음 → keyword fallback 결과
```

이는 hybrid 검색이 아니다. hybrid는 같은 질문에 dense와 keyword를 둘 다 실행하고 점수 합산이나
RRF로 하나의 순위를 만드는 방법이다. 현재는 어느 응답에서도 두 점수가 함께 순위에 영향을 주지
않는다. BM25, hybrid, RRF와 reranker는 승인 gold에서 현재 exact dense보다 실제 근거 품질을
개선하는지 검증하기 전에는 도입하지 않는다. HNSW는 이 후보군과 다르다. 현재와 미래의 운영·실험
검색에서 영구 제외했으며 검증 후 재검토 항목도 아니다.

keyword fallback도 사용자 문장을 그대로 DB 검색 문법으로 실행하지 않는다. NFKC 정규화 후
질문형 표현과 조사를 제거하고 한글·영문·숫자 토큰으로 서버가 검색식을 만든다.

1. 모든 핵심어가 일치하는 후보를 찾는다.
2. 없으면 최소 두 핵심어 조합의 후보 pool을 만든다.
3. 그 후보에 정확 법령명·기술기준명 또는 통제 도메인 앵커가 있는지 검사한다.
4. 안전한 후보가 없으면 전체 단일어 OR로 넓히지 않고 근거 부족으로 끝낸다.

`확인`, `알려주세요`, `절차` 같은 질문 표현 때문에 원문 검색이 0건이 되는 문제를 줄이면서도, 일반어
하나만 같은 조문을 법률 근거로 올리지 않기 위한 절충이다.

## 임베딩과 코사인을 최소한으로 이해하기

임베딩은 문자열을 여러 실수 좌표로 바꾼 벡터다. **차원**은 좌표의 개수다. 512차원 벡터는 숫자
512개로 이루어지지만, 각 좌표 하나에 사람이 붙일 수 있는 고정 의미가 있는 것은 아니다. 학습된
공간에서 텍스트 관계가 좌표 전체의 방향과 거리로 표현된다.

**내적** `a · b`는 같은 위치의 좌표끼리 곱한 뒤 모두 더한 값이다. 방향이 비슷하고 크기도 큰 벡터는
내적이 커질 수 있다. **norm**은 벡터의 길이이며 L2 norm은 각 좌표의 제곱을 더한 뒤 제곱근을 취한다.
**L2 정규화**는 각 좌표를 그 길이로 나눠 벡터 길이를 1로 만드는 일이다.

두 벡터 `a`, `b`의 코사인 유사도는 다음과 같다.

```text
cosine(a, b) = (a · b) / (||a||₂ × ||b||₂)
```

**코사인 유사도**는 내적을 두 벡터 길이로 나눠 크기 영향을 제거하고 방향이 얼마나 비슷한지 본다.
두 벡터가 L2 norm 1이면 분모가 1이므로 내적과 코사인 유사도가 같다. 점수 `0.9`는 90% 정답이라는
확률도, 법률적으로 같은 의미라는 판정도 아니다. 관련·비관련 gold에서 순위를 평가해야 한다.

현재 embedding profile은 다음 변환을 하나의 계약으로 묶는다.

```text
provider/model: NVIDIA / nvidia/nemotron-3-embed-1b
문서 입력: passage
질문 입력: query
NIM 출력: 2048차원
저장·검색: 앞 512개 선택 후 L2 재정규화
본문 템플릿: 법령명 + 경로 + 표제 + 본문
```

512차원은 업계 표준이 아니다. NIM API는 이 모델에서 2048차원만 반환하므로 `dimensions=512` 요청은
API 계약상 사용할 수 없다. 대신 NVIDIA 모델 카드는 학습된 prefix 축약 방식으로 첫 1024개 또는 첫
512개 좌표를 유지하도록 명시한다. 현재 저장 계약이 512차원이므로 공식 선택지 중 앞 512개를 쓴다.

뒤 1,536개를 버리면 그 정보와 원래 2048차원 방향은 사라진다. 자른 벡터의 길이는 대개 1보다
작아지므로 남은 각 좌표를 잘린 벡터의 L2 norm으로 다시 나눈다. 이 **재정규화**는 512개 좌표끼리의
비율과 새 512차원 공간 안의 방향은 유지하면서 길이만 1로 복원한다. 삭제한 좌표나 원래 방향을
복구한다는 뜻은 아니다. 공식 계약과 선택 근거는
[NVIDIA Nemotron 3 Embed 1B 조사](../references/nvidia-nemotron-3-embed-1b-2026-07-23.md)에 있다.

차원이 같아도 다른 모델의 벡터는 같은 공간이 아니다. 그래서 모델명뿐 아니라 native/stored 차원,
query/passage 입력 유형, 축약, 정규화, 텍스트 템플릿과 version이 모두 같은 profile key일 때만 질문과
문서 벡터를 비교한다. 각 문서 벡터에는 실제 입력 문자열 SHA-256을 저장해 본문·표제·경로·법령명이
바뀐 낡은 벡터를 제외한다.

## 검색 후보와 답변 문맥은 다르다

검색의 목표는 필요한 근거를 놓치지 않는 것이고, 답변 문맥의 목표는 무관한 내용 없이 직접 근거를
제공하는 것이다. 따라서 `top 10 후보`와 `모델에 넣을 문맥 수`는 같은 값일 필요가 없다.

파서는 조·항·호·목을 작은 검색 단위로 저장한다. 그대로 두면 같은 제7조의 여러 하위 조각이 순위를
독점할 수 있다. production은 문서와 조문 root별로 묶어 같은 조에서 가장 높은 청크 하나를 대표로
남기고, 서로 다른 조문을 최대 5개까지 문자 예산 안에서 생성 모델에 전달한다.

```text
raw 청크 후보
→ 같은 조문 root로 grouping
→ 서로 다른 조문 후보
→ 최대 5개 생성 문맥
```

grouping은 AI reranking이 아니다. 이미 계산된 순위에서 같은 조의 중복을 결정적으로 줄이는 단계다.
실험 D의 검색 평가는 dense 자체를 qrels와 비교해야 하므로 이 production grouping을 우회하고 raw
`provision_id` 순위를 사용한다.

## 작은 확인셋을 Gold처럼 부르지 않는다

D-10의 10문항은 사용자가 직접 근거와 문맥 판정을 확인했으므로 같은 저장 후보를 비교하는 calibration에는
쓸 수 있다. 그러나 판정 범위는 원래 raw top 10과 알려진 top 5 무관 후보에 한정되고, 독립 주석·전체
후보 qrels·held-out split이 없다. 따라서 hit@K와 첫 근거 순위는 `manual diagnostic`이며 Evidence Recall과
모집단 성능이 아니다.

이 구분은 재정렬에서 특히 중요하다. 원래 6~10위 후보가 새 top 5로 올라오면 기존에 무관으로 표시되지
않았다는 이유만으로 관련 후보가 되지 않는다. `known irrelevant@5` 감소와 실제 Precision@5 개선은 다르며,
새 top 5를 다시 사람이 판정해야 한다.

현재 M2는 질문·판정·직접 근거 ID·snapshot/profile·artifact SHA를 10문항 계약으로 동결한다. M3는 새
검색을 하지 않고 이 계약과 저장 raw/R1 순위로 소표본 분석만 수행한다. 1,000문항 질문은행은 삭제하지
않되 일반화나 운영 회귀가 필요할 때 현재 corpus를 다시 검사하고 필요한 Gold를 작성한다.

전 후보 qrel을 만든다는 것은 positive provision만 추가하는 일이 아니다. D-10 전수 workflow는 각 질문에
현재 3,066개 provision을 모두 배치하고 positive를 제외한 나머지도 relevance 0으로 명시해 총 30,660개
판정을 만든다. 그래야 검색 결과에 없던 provision을 미판정인데 무관한 것으로 간주하는 오류를 피할 수 있다.

다만 자동 또는 assistant 일괄 relevance-0은 그 자체로 adjudicated negative가 아니다. 사용자는 positive
원문뿐 아니라 음성 판정의 범위·검색 방법·누락 가능성을 문항별로 승인해야 한다. 수정이 있으면 기존 draft를
직접 고치지 않고 annotation proposal revision을 새로 만들고 전체 judgment SHA를 다시 봉인한다. 이처럼
`complete candidate coverage`와 `independent human confidence`는 별개의 품질 축이다.

검색 점수가 높아도 직접 근거가 아닐 수 있다. “전기사업 허가권자는 누구인가?”에 대해 허가라는 단어가
있는 다른 의무 조문은 주제가 비슷하지만 질문의 주체를 답하지 못할 수 있다. similarity cutoff 하나를
법률적 `insufficient_evidence` 판정으로 쓰지 않는 이유다.

## 검색 후처리기를 정답 판정기로 오해하지 않는다

LlamaIndex 같은 라이브러리에서 `Node Postprocessor`는 검색 결과를 답변 합성 전에 가공하는 공통
확장 지점이다. `SimilarityPostprocessor`는 그 구현 중 하나로, 이미 계산된 `node.score`가 cutoff보다
낮으면 제거할 뿐 새 임베딩이나 AI 판단을 하지 않고 순서도 새로 정하지 않는다.

```text
Node Postprocessor
├─ SimilarityPostprocessor  # 기존 점수의 임계값 필터
├─ KeywordPostprocessor     # 키워드 규칙 필터
├─ model reranker           # 질문+후보를 모델로 다시 채점
└─ PrevNextPostprocessor    # 인접 노드 추가
```

검증된 점수 분포가 있다면 similarity cutoff는 값싼 잡음 제거 도구가 될 수 있다. 그러나 코사인 점수는
정답 확률이 아니므로 cutoff는 직접 근거, 법적 충분성이나 `insufficient_evidence`를 판정하지 못한다.
reranker도 질문과 후보의 관련성을 더 세밀하게 재채점하는 모델이지 법률 답을 생성하거나 인용 충분성을
자동 보장하는 장치가 아니다. 현재 제품에는 이 LlamaIndex 후처리기나 reranker를 넣지 않았다. 개념의
공식 자료와 프로젝트 적용 경계는 [RAG 검색·근거 선택 참고 자료](../references/rag-retrieval-patterns-2026-08-03.md)에 있다.

## 구조화 출력과 인용 gate

API는 검색 결과에 요청 안에서만 쓰는 `C1`, `C2` 같은 citation ID를 붙인다. 생성 모델은 자유로운
Markdown 대신 요약·주장·설명·체크리스트와 각 항목의 citation ID를 구조화 schema로 반환한다. 서버는
schema 검증 뒤에도 초안을 신뢰하지 않는다.

결정적 gate는 최소한 다음을 확인한다.

1. 답변 section과 checklist가 비어 있지 않은가?
2. 모든 실질 항목에 citation ID가 있는가?
3. 그 ID가 이번 검색에서 제공한 ID인가?
4. 핵심 용어의 충분한 부분이 인용 원문에 있는가?
5. 허가·신고·등록·금지·면제·벌칙 같은 규범어가 원문에도 직접 있는가?
6. 주장에 쓴 숫자가 원문에도 있는가?
7. 링크와 citation 객체를 서버가 허용한 공식 출처·버전·조문으로 다시 조립할 수 있는가?

이 gate는 완전한 법률 의미 판정기가 아니다. 존재하지 않는 인용, 근거에 없는 규범 유형과 숫자 같은
위험을 낮추는 보수적 하한선이다. 하나라도 실패하면 초안을 버리고 검색 원문과 한계를 보여 주는
검색 전용 응답으로 전환한다. 다른 생성 모델로 조용히 바꾸지 않는다.

## 검색 실패를 디버깅하는 순서

모든 실패를 “AI가 답하지 못했다”로 묶으면 검색 0건을 프롬프트 변경으로 숨길 수 있다. 다음 경계를
순서대로 본다.

1. 입력: 질문, 기준일, 모드와 인증 주체
2. 파싱: 직접 경로인지 자연어인지, 정규화한 경로
3. 질의 변환: 제거한 표현, 핵심어, 앵커, 실제 keyword 단계
4. 코퍼스: 기대 원문·버전·조문 존재, 지원 날짜와 준비 gate
5. 검색: 단계별 후보 수, 최종 raw 후보와 시간
6. 임베딩: profile, query 생성, 벡터 coverage와 SHA
7. 생성: 검색 근거가 있을 때만 provider·schema·인용 gate
8. 결과: 근거 반환, no results, 저장소 장애, 생성 폴백을 분리

질문 원문·원문 전문·인증정보·provider 오류 전문은 로그에 남기지 않는다. 로그인 이력에는 필요한
단계 상태와 후보 수만 구조화해 보존한다.

## 직접 확인

```powershell
uv run --directory apps/api python -m scripts.backfill_embeddings verify `
  --query "태양광 발전 설비는 법에서 어떻게 정의하나요?" --limit 3
```

권위 구현 계약은 [RAG 파이프라인](../design-docs/rag-pipeline.md)과
