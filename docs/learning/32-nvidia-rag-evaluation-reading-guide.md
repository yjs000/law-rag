# NVIDIA RAG 평가를 한 질문으로 이해하기

확인일: 2026-08-03

NVIDIA의 RAG 평가 문서를 처음 읽으면 지표 이름부터 막힌다. `Recall@K`, `nDCG`, `Context Precision`, `Faithfulness`가 한 표에 섞여 있고, 문서마다 나오는 목록도 조금씩 다르다.

하지만 이 지표들은 모두 같은 질문을 한다.

> **RAG가 좋은 답을 만들기까지, 어느 단계가 잘했고 어느 단계가 실패했는가?**

이 글에서는 계산식부터 외우지 않는다. 도서관에서 질문에 답하는 과정을 따라가며 각 지표가 맡은 역할을 이해한다. 정확한 계산식과 용어 사전이 필요하면 [31 RAG 평가 지표](31-rag-evaluation-metrics.md)를 함께 보면 된다.

## 먼저 RAG를 네 사람의 협업으로 생각하자

RAG 시스템을 도서관의 네 사람으로 비유할 수 있다.

1. **사서**가 질문과 관련된 자료를 넉넉하게 찾는다.
2. **편집자**가 찾은 자료에서 답변에 쓸 부분만 고른다.
3. **작성자**가 선택된 근거를 읽고 답변을 쓴다.
4. **검증자**가 답변과 인용이 실제 근거에 맞는지 검사한다.

```text
질문
  ↓
사서: 후보 검색
  ↓
편집자: 최종 문맥 선택
  ↓
작성자: 답변 생성
  ↓
검증자: 근거·정답·인용 확인
```

한 사람의 성적만 보고 전체 시스템을 판단할 수는 없다. 사서가 틀린 책을 가져왔는데 작성자가 그 책에 충실하게 답할 수도 있다. 이때 답변의 `Faithfulness`는 높지만 검색 품질과 최종 정답성은 낮다.

RAG 지표가 여러 개인 이유가 바로 이것이다.

## NVIDIA 문서가 서로 달라 보이는 이유

NVIDIA에는 하나의 고정된 “RAG 총점표”만 있는 것이 아니다. 제품과 문서의 목적에 따라 보는 단계가 다르다.

- **NeMo Microservices 25.8 문서**는 문서 검색과 답변 생성을 분리한다. 검색에는 `Recall@K`와 `nDCG@K`를 제시하고, 답변 생성에는 Faithfulness·Answer Relevancy·Answer Correctness·Context Precision·Context Recall 등을 제시한다.
- **현재 NeMo Platform 문서**는 RAGAS 기반의 문맥·응답 평가에 초점을 둔다. Context Recall·Context Precision·Context Relevance·Faithfulness·Response Relevancy·Noise Sensitivity 등의 입력과 실행 방법을 설명한다.
- **NVIDIA RAG Blueprint 벤치마크 문서**는 완성된 RAG 구성끼리 최종 답변 정확도를 비교한다. 여기서는 LLM 심사자가 답변에 0~4점을 주고 정규화하는 Answer Accuracy 방법을 사용한다.

목록이 다른 것은 서로 모순돼서가 아니다. **제품 버전과 평가하려는 구간이 다르기 때문**이다. 따라서 지표 이름을 보기 전에 “지금 검색기를 평가하는가, 문맥을 평가하는가, 최종 답변을 평가하는가?”부터 확인해야 한다.

## 하나의 질문을 네 칸에 담아 보자

현재 NeMo Platform의 RAG 평가는 대체로 다음 네 가지 값을 사용한다.

| 값 | 쉬운 뜻 | 예시 |
|---|---|---|
| `user_input` | 사용자의 질문 | 태양에너지는 법에서 어떻게 분류되나요? |
| `retrieved_contexts` | 검색해서 가져온 본문들 | 태양에너지 정의 조문, 무관한 송전 조문 |
| `response` | RAG가 생성한 답변 | 태양에너지는 재생에너지에 해당합니다. |
| `reference` | 사람이 준비한 기준 답변 | 질문에 필요한 정답과 핵심 근거 |

이 예시는 지표를 설명하기 위한 가상 사례다. 실제 법률 답변이나 실제 실험 결과가 아니다.

모든 지표가 네 값을 전부 쓰는 것은 아니다. 예를 들어 검색 문맥의 누락을 보려면 질문·문맥·기준 답변이 필요하고, 생성 답변의 충실성을 보려면 응답과 검색 문맥이 필요하다. **필요한 입력이 없으면 그 지표가 무엇을 측정하는지부터 성립하지 않는다.**

## 1단계: 사서는 정답 근거를 찾았는가

검색 단계의 첫 목표는 답을 가진 자료를 후보 안에 넣는 것이다.

### Recall@K: 정답을 놓치지 않았는가

`Recall`은 “찾아야 할 것을 얼마나 빠뜨리지 않았는가”다. `@K`는 상위 K개 결과까지만 본다는 뜻이다.

예를 들어 정답 조문이 검색 결과 7위라면 다음처럼 해석한다.

- Recall@3: 실패
- Recall@5: 실패
- Recall@10: 성공

Recall@10이 높다는 것은 사서가 넉넉한 후보 안에는 정답을 가져왔다는 뜻이다. 하지만 작성자에게 10개를 전부 주어도 된다는 뜻은 아니다. 불필요한 조문이 너무 많으면 오히려 답변을 방해할 수 있다.

### nDCG@K: 좋은 근거가 앞에 있는가

Recall은 정답이 1위인지 10위인지 구분하지 못한다. `nDCG`는 더 직접적인 근거가 앞 순위에 있을수록 높은 점수를 준다.

태양에너지 질문에서 다음 두 결과는 Recall@3이 모두 성공할 수 있다.

```text
검색 A: 1위 태양에너지 정의 / 2위 보조 조문 / 3위 무관 조문
검색 B: 1위 무관 송전 조문 / 2위 보조 조문 / 3위 태양에너지 정의
```

그러나 검색 A의 nDCG가 더 높다. 사용자가 먼저 볼 결과와 다음 단계가 먼저 사용할 근거의 순서까지 평가하기 때문이다.

검색기를 바꿨다면 우선 Recall@K로 누락을 확인하고, nDCG@K로 순서가 좋아졌는지 확인한다.

## 2단계: 편집자는 쓸 만한 문맥을 골랐는가

사서가 top 10을 가져온 뒤 편집자가 답변에 쓸 3~5개만 고른다고 하자. 이때부터는 단순한 검색 순위보다 **최종 문맥의 충분함과 잡음**이 중요하다.

### Context Recall: 답에 필요한 정보가 다 들어 있는가

Context Recall은 기준 답변에 필요한 정보가 검색 문맥에 얼마나 포함됐는지를 본다.

태양에너지가 재생에너지라는 문구는 가져왔지만, 질문이 요구한 예외나 요건을 담은 항을 빠뜨렸다면 Context Recall이 낮아질 수 있다.

이 지표가 답하는 질문은 단순하다.

> 이 문맥만 읽고 기준 답변을 빠짐없이 만들 수 있는가?

### Context Precision: 직접 도움이 되는 문맥이 앞에 있는가

Context Precision은 도움이 되는 청크가 무관한 청크보다 앞에 놓였는지 본다. 일반적인 Precision처럼 관련 청크의 개수만 세는 것이 아니라, 관련 청크가 나타난 순서도 반영한다.

```text
좋은 문맥: 직접 정의 → 필요한 예외 → 참고 설명
나쁜 문맥: 송전사업 → 배전사업 → 직접 정의
```

두 경우 모두 직접 정의를 포함하지만, 두 번째는 생성 모델이 잡음에 먼저 노출된다.

### Context Relevance: 질문 주제와 관련 있는가

Context Relevance는 문맥이 질문의 주제와 얼마나 관련 있는지 본다. 기준 답변이 없어도 활용할 수 있다는 장점이 있다.

그러나 “태양광과 전력 분야에 관한 글”과 “태양에너지의 법적 분류를 직접 설명하는 조문”은 다르다. 주제가 비슷하다고 직접 근거가 되는 것은 아니다. 그래서 Context Relevance 하나만으로 `insufficient_evidence`를 결정하면 위험하다.

### Context Entity Recall: 중요한 이름이 빠지지 않았는가

`Entity`는 법률명·기관·사람·지역처럼 구별되는 중요 개체다. Context Entity Recall은 기준 답변의 중요 개체가 문맥에 들어 있는지 본다.

이 지표는 “산업통상자원부장관” 같은 핵심 주체의 누락을 찾는 데 유용하다. 하지만 개체 이름이 모두 있다고 법적 관계까지 맞는 것은 아니다. 누가 누구에게 무엇을 허가하는지는 본문 관계를 별도로 읽어야 한다.

## 3단계: 작성자는 근거 안에서 질문에 답했는가

좋은 문맥을 골랐어도 답변을 잘못 쓸 수 있다. 이 단계에서는 “근거를 벗어나지 않았는가”와 “질문에 제대로 답했는가”를 나누어 본다.

### Faithfulness: 답변의 주장이 문맥에 있는가

Faithfulness는 생성 답변의 각 주장이 제공된 검색 문맥으로 뒷받침되는지를 본다.

```text
문맥: 태양에너지는 재생에너지에 해당한다.
답변: 태양에너지는 재생에너지이며 모든 사업자는 자동으로 허가된다.
```

첫 번째 주장은 문맥에 있지만 두 번째 주장은 없다. 이 답변은 문맥 밖 내용을 추가했으므로 Faithfulness가 낮아져야 한다.

중요한 함정이 있다. 틀린 문맥만 제공하고 답변이 그 틀린 문맥을 그대로 따르면 Faithfulness는 높을 수 있다. Faithfulness는 **검색이 맞았다는 점수도, 최종 답이 정답이라는 점수도 아니다.**

### Response Groundedness: 답변이 제공된 근거에 발을 딛는가

Groundedness도 답변이 제공된 문맥에 근거하는지를 본다. Faithfulness와 의미 영역이 많이 겹친다. 다만 실제 구현에서는 심사 프롬프트와 주장 분해 방식이 달라 별도 점수로 제공될 수 있다.

두 이름이 있다고 반드시 둘 다 핵심 지표로 써야 하는 것은 아니다. 프로젝트에서는 하나를 주 지표로 정하고, 다른 하나는 판정이 엇갈리는 사례를 조사하는 보조 지표로 쓰는 편이 해석하기 쉽다.

### Response Relevancy: 질문에 정면으로 답했는가

Response Relevancy는 답변이 사용자의 질문을 직접 다루는지 본다.

```text
질문: 태양에너지는 법에서 어떻게 분류되나요?
답변: 신재생에너지 정책은 산업 발전에 중요합니다.
```

답변은 같은 주제를 말하지만 분류를 답하지 않았다. 근거에 어긋난 말이 없더라도 relevancy는 낮아야 한다.

반대로 질문에 정면으로 답했지만 사실이 틀릴 수도 있다. **관련성은 정답성이 아니다.**

### Noise Sensitivity: 무관한 자료에 흔들리는가

Noise Sensitivity는 정답 문맥 사이에 무관한 문맥이 섞였을 때 답변이 얼마나 영향을 받는지 본다. NVIDIA 문서는 이 값이 낮을수록 일반적으로 잡음에 덜 민감하다고 설명한다.

같은 질문을 다음 두 조건으로 실행해 비교할 수 있다.

1. 직접 근거만 제공한다.
2. 직접 근거와 무관한 송전·배전 조문을 함께 제공한다.

두 번째 조건에서 답변이 무관한 내용을 끌어오면 잡음에 민감한 시스템이다.

## 4단계: 최종 답은 실제로 맞는가

Answer Correctness나 Answer Accuracy는 생성 답변을 기준 답변과 비교해 실제 정답에 가까운지 본다. NeMo Microservices의 버전 문서와 RAG Blueprint 벤치마크에서 이 계열의 지표를 확인할 수 있다.

RAG Blueprint의 공개 벤치마크는 LLM 심사자가 답변에 0~4점을 주고 이를 정규화한다. 이 결과를 읽을 때는 생성 모델뿐 아니라 평가에 사용한 심사 모델과 설정도 함께 봐야 한다.

최종 정답성이 높아도 인용이 맞다는 보장은 없다. 모델이 학습 중 기억한 사실로 우연히 정답을 냈을 수 있기 때문이다. 법률 RAG에서는 다음 검사를 별도로 해야 한다.

- 각 실질 주장에 인용이 붙었는가
- 인용한 본문이 바로 그 주장을 지원하는가
- 인용 ID·조문 경로·문서 버전·SHA가 실제 원문과 연결되는가

## 실패 사례를 보면 지표가 더 잘 보인다

| 관찰한 실패 | 먼저 볼 지표 | 해석 |
|---|---|---|
| 정답 조문이 후보에 없음 | Recall@K | 사서가 근거를 놓쳤다 |
| 정답은 있지만 무관한 조문 뒤에 있음 | nDCG@K, Context Precision | 순위 또는 문맥 정리가 나쁘다 |
| 필요한 항·호 일부가 빠짐 | Context Recall | 답을 완성할 정보가 부족하다 |
| 답변이 근거에 없는 내용을 추가함 | Faithfulness, Groundedness | 작성자가 근거 밖으로 나갔다 |
| 답변이 질문을 피해 감 | Response Relevancy | 질문의 요구를 직접 처리하지 않았다 |
| 무관한 문맥을 넣자 답변이 바뀜 | Noise Sensitivity | 잡음에 취약하다 |
| 틀린 문맥을 충실하게 요약함 | 높은 Faithfulness + 낮은 Correctness | 검색과 문맥 선택이 먼저 실패했다 |
| 근거 없이 우연히 정답을 말함 | 높은 Correctness + 낮은 Faithfulness | 모델 기억에 의존했을 수 있다 |

이 표에서 가장 중요한 사실은 **한 점수가 높아도 다른 단계는 실패할 수 있다**는 것이다.

## LLM 심사 점수는 체온계가 아니다

현재 NeMo Platform의 여러 RAGAS 지표는 별도의 `judge LLM`이 문맥과 답변을 읽고 판정한다. Response Relevancy는 심사 LLM뿐 아니라 임베딩 모델도 필요하다.

LLM 심사자는 의미를 읽을 수 있지만 절대적인 측정 기구는 아니다. 모델·프롬프트·샘플링 설정에 따라 점수가 달라질 수 있고, 호출 실패로 점수가 계산되지 않을 수도 있다.

따라서 평가 기록에는 최소한 다음을 남겨야 한다.

- 심사 모델 이름과 버전
- 평가 프롬프트 또는 평가기 버전
- 실행 시각과 입력 데이터 버전
- 계산 실패와 `NaN`의 개수
- 사람이 만든 정답표와 심사 결과가 얼마나 일치하는지

반면 Recall@K처럼 문서 ID와 정답표로 계산하는 지표는 같은 입력에서 같은 결과를 내기 쉽다. **결정적 검색 지표와 LLM 심사 지표를 한 종류의 숫자처럼 섞지 않는 것**이 중요하다.

## Offline과 Online 평가는 무엇이 다른가

현재 NeMo Platform 문서는 두 실행 방식을 구분한다.

- **Offline 평가**: 이미 생성해 둔 `response`를 평가한다. 같은 출력을 다시 검사하므로 비교와 재현에 유리하다.
- **Online 평가**: 평가 실행 중 시스템이 답변을 새로 생성한 뒤 평가한다. 실제 전체 흐름을 볼 수 있지만 생성 변동성까지 결과에 섞인다.

여러 번 실행했을 때 결과가 같은지 확인하려면 먼저 실제 응답을 저장하는 Offline 평가가 이해하기 쉽다. 생성 모델을 바꾼 전체 체인의 결과를 보고 싶을 때 Online 평가를 추가한다.

## 이 법률 RAG에 적용하는 가장 단순한 평가 순서

다음은 NVIDIA의 공식 필수 설정이 아니라, 공식 지표의 역할을 이 프로젝트 구조에 맞춰 배치한 **프로젝트 적용안**이다.

### 검색 후보 단계

1. 법률 원문 ID·조문 경로·버전·SHA가 맞는지 먼저 검증한다.
2. 고정 질문과 정답 조문 표로 Recall@1·3·5·10을 계산한다.
3. 직접 근거와 보조 근거에 등급을 주고 nDCG를 계산한다.
4. 조문 ID뿐 아니라 실제 답변 문구가 후보에 있는지 Evidence Recall을 확인한다.

### 최종 문맥 선택 단계

1. top 10 후보에서 답변에 쓸 소수의 근거를 선택한다.
2. Context Recall로 필요한 근거의 누락을 본다.
3. Context Precision과 Evidence Precision으로 잡음이 줄었는지 본다.
4. 범위 밖 질문은 억지 근거를 선택하지 않고 `insufficient_evidence`로 보내는지 검사한다.

### 답변 생성 단계

1. Faithfulness로 근거 밖 주장을 찾는다.
2. Response Relevancy로 질문을 직접 답했는지 본다.
3. Answer Correctness로 기준 답변과 사실이 맞는지 본다.
4. 주장별 인용 정확성·범위·원문 무결성을 별도로 검증한다.

`insufficient_evidence`는 코사인 점수 하나로 정하지 않는다. 답할 수 없는 질문을 잘못 답한 비율과, 답할 수 있는 질문을 잘못 거부한 비율을 함께 봐야 한다. 그래야 안전성만 높이려다 모든 질문을 거부하는 시스템을 좋은 시스템으로 오해하지 않는다.

## 무엇을 바꿨는지에 따라 지표를 고르자

| 변경한 부분 | 우선 확인할 것 |
|---|---|
| 임베딩·검색 방식 | Recall@K, nDCG@K, 첫 정답 순위 |
| top 10에서 최종 문맥을 고르는 방식 | Context Recall, Context Precision, Evidence Precision |
| 생성 모델·프롬프트 | Faithfulness, Response Relevancy, Answer Correctness |
| 잡음 제거 방식 | Noise Sensitivity |
| 근거 부족 판정 | 답변 불가 질문 오답률, 잘못된 거부율 |
| 인용 생성 방식 | Citation Correctness, Citation Coverage, source integrity |

모든 지표를 매번 돌리는 것보다, **이번 변경이 영향을 주는 단계의 지표를 먼저 고르는 것**이 비용도 적고 원인도 잘 보인다.

## 한 문장으로 정리

RAG 평가는 하나의 총점을 찾는 일이 아니다. **검색이 정답을 회수했는지, 선택한 문맥이 충분하고 깨끗한지, 답변이 질문과 근거에 충실한지, 최종 주장과 인용이 실제로 맞는지를 단계별로 확인하는 일**이다.
