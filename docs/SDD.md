# 명세 주도 개발(SDD) 운영 규칙

## 1. 목적

구현 전에 사용자 가치, 범위, 불변조건과 검증 가능한 수용 기준을 SPEC으로 고정한다. 구현 계획, 코드, 테스트와 완료 판정은 승인된 SPEC을 추적한다. 개발 skill의 선택과 세부 실행 절차는 설치된 Superpowers의 trigger 조건을 따르며, 이 문서는 law-rag의 문서 정본과 Codex 모델 배정을 정의한다.

## 2. 문서의 정본 역할

| 문서 | 정본으로 관리하는 내용 |
| --- | --- |
| `AGENTS.md` | 저장소 공통 규칙과 작업 시작 순서 |
| `docs/CURRENT_STATE.md` | 현재 작업의 시작 포인터 |
| `docs/PRODUCT_SENSE.md` | 사용자 가치와 제품 범위 |
| `ARCHITECTURE.md` | 시스템 경계와 의존 방향 |
| `docs/product-specs/` | 사용자 동작과 수용 기준 |
| `docs/design-docs/` | 기술 설계와 결정 |
| `docs/exec-plans/{todo,active,completed,dropped}/` | 실행 단계, 상태, 검증과 결과 |
| `docs/ROADMAP.md` | 실행계획 헤더에서 생성한 작업 색인 |
| `docs/references/agent-runtime-policy.md` | Windows Python 및 GitHub 인증 등 조건부 런타임 절차 |

같은 규칙을 여러 문서에 복제하지 않는다. 로드맵의 상태를 직접 편집하지 않으며, 실행계획 헤더를 바꾼 뒤 `python scripts/render_roadmap.py`로 재생성한다. 세부 상태 전이는 `docs/PLANS.md`와 `roadmap-operator`를 따른다.

## 3. 개발 흐름

1. 작업 목적, 범위와 제약을 판단한다.
2. 필요한 제품·기술 SPEC에 동작, 불변조건, 정상·실패·경계 사례와 수용 기준을 적고, 적용 중인 승인 절차를 따른다.
3. SPEC을 참조하는 실행계획에 변경 범위와 검증 명령을 연결한다.
4. 작업 난이도에 맞는 구현을 수행한다. 테스트·문서와 코드를 같은 변경에서 맞춘다.
5. 최신 TEST 결과를 확인하고 SPEC 수용 기준과 대조한다.
6. 문제가 있으면 원인을 판단해 수정 범위를 정하고 4~5단계를 반복한다. 완료 조건이 충족되면 실행계획 결과와 로드맵을 갱신한다.

법률 근거·인용, 개인정보, 도메인 경계와 검증의 불변조건은 `AGENTS.md`와 관련 권위 문서를 따른다. 명세가 바뀌면 실행계획·코드·테스트의 연결도 함께 갱신한다.

## 4. 최소 읽기와 컨텍스트

작업 시작에는 `AGENTS.md`와 `docs/CURRENT_STATE.md`의 지정 범위, 선택한 실행계획 헤더와 선언된 참고 범위만 읽는다. 모델 정책이 필요한 때 이 문서의 6절을 읽고, Windows Python 또는 GitHub 인증 절차가 필요할 때만 런타임 정책의 해당 절을 읽는다. 실패 재시도에는 전체 대화 대신 실패 증거와 변경된 전제를 전달한다.

## 5. 실행계획과 상태

작업의 ID, 상태, 다음 행동과 참고 범위는 실행계획 헤더가 정본이다. `Picked Up`과 오케스트레이션 하위 작업의 선택·전이는 `docs/PLANS.md` 및 `roadmap-operator`에 따른다. 별도 작업을 임의로 현재 범위에 추가하거나 완료되지 않은 수용 기준을 다음 작업으로 넘기지 않는다.

## 6. 에이전트 단계와 GPT-6 모델 정책

Codex 개발 작업은 **판단 → SPEC → 구현 → TEST·SPEC 준수 검토** 순서로 진행한다. 문제가 발견되면 원인을 판단해 수정하고 TEST·준수 검토를 반복한다. 사용자 요청이나 적용 중인 workflow가 허용한 경우에만 별도 subagent에 위임하며, 직접 수행할 때도 같은 순서를 따른다.

| 단계 | 역할 | 모델 | reasoning effort |
| --- | --- | --- | --- |
| 판단·SPEC | 범위와 난이도 판단, 수용 기준 명세 | `gpt-6-sol` | `medium` |
| 단순 task | 명확하고 국소적인 구현 | `gpt-6-luna` | `max` |
| 어려운 task | 복잡한 구현·통합·디버깅 | `gpt-6-sol` | `low` |
| TEST·SPEC 준수 검토 | 최신 테스트 결과와 승인된 수용 기준 대조 | `gpt-6-sol` | `low` |
| 문제 발견 시 | 원인 판단, 수정 범위 결정, 재검증 지시 | `gpt-6-sol` | `medium` |

- 단순/어려운 task는 파일 수가 아니라 명세의 명확성, 계약·통합 복잡도, 실패 원인 분석 필요성으로 구분한다.
- 승인된 SPEC과 기존 완료·검증 조건을 유지한다. 준수 검토에서 문제를 찾으면 해당 구현 단계로 돌려보내고, 수정 후 TEST와 SPEC 준수 검토를 다시 수행한다.
- Subagent dispatch 시 위 표의 `model`과 `reasoning_effort`, 필요한 최근 turn만 담은 `fork_turns`를 명시한다. 사용할 수 없는 조합을 임의로 다른 모델로 대체하지 않는다.
- 모델 지정이 불가능한 시스템 내부 agent에는 이 배정표를 적용하지 않는다. Subagent 결과만으로 부모 작업의 완료를 선언하지 않는다.

## 7. 검증과 완료

승인된 수용 기준, 정상·실패·경계 사례, 관련 테스트와 문서, `AGENTS.md`의 검증 계약을 최신 변경 상태에서 확인한다. TEST 또는 SPEC 준수 검토에서 발견한 현재 작업의 문제는 수정·재검증 전까지 완료로 판정하지 않는다. subagent의 완료 보고는 부모의 최종 검증을 대신하지 않는다.
